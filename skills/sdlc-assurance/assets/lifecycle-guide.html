02 / Proportional depth

Validation by risk tier

Use the highest credible consequence and uncertainty. A tiny diff can be H. H selects relevant methods; it does not require every test type.

This selector changes guidance only. It does not assign a project's risk tier or measured status.

Required checks and unresolved gaps

Every in-scope acceptance criterion, consequential risk/control, and mandatory activity needs a required check or valid accepted exception. Record applicability, candidate, environment, result, evidence and owner. Missing coverage keeps the gate NOT_READY unless an unresolved FAIL or BLOCKED takes precedence.

Use the existing workflow

Scale records to the change. A small reversible edit may need a short acceptance note and direct inspection. Reuse repository workflows and existing evidence; do not create paperwork without a purpose.

Record unresolved applicability

An unavailable environment is BLOCKED. Unresolved applicability makes the gate NOT_READY unless a higher-precedence unresolved FAIL or BLOCKED applies. Neither becomes NOT_APPLICABLE to make progress appear complete.

Retain attempts and findings

Preserve every attempt. A later pass does not erase an earlier failure: link its cause or demonstrated invalidity, correction, current candidate and clean revalidation. An observed in-scope violation is a FAIL even when found by an optional or exploratory check; triage consequential unresolved signals before PASS.

UI creation and redesign

Custom UI design

Rethink the affected interface for this project’s users, domain, content and workflows. Establish its maturity, brand/design system, native platform, architecture/components, accessibility/support matrix, budget and authorized scope. Distinguish observed context from assumptions. Explore suitable structures when needed, then design the hierarchy, task flow, layout, typography and state behavior; record why the approach fits.

Do not use premade page, dashboard or landing-page templates, including restyled templates. Native controls, tested accessible components and design-system tokens remain useful building blocks. Preserve product requirements and useful interaction conventions; change only relevant screens. Custom design does not require novelty or a rewrite. A typo fix or backend-only change does not authorize a full redesign. Evidence-record formats may be reused.

For design-only work, validate the agreed prototype and record remaining implementation checks. When implementation is in scope, validate the connected journey, relevant success/error/denial/recovery states, responsive behavior and accessibility. Retain candidate-bound visual and functional evidence; label simulated behavior. Follow the custom UI design process.

03 / Traceability

Requirements, risks, checks, and evidence

Follow the chain in either direction: each claim needs evidence, and each material requirement and risk needs a verification route.

  1. RequirementWhat outcome and invariant must hold?
  2. RiskWhat could go wrong, and for whom?
  3. DesignWhich control or decision addresses it?
  4. TestWhat observation could disprove the claim?
  5. EvidenceWhich candidate, conditions and result?
  6. ClaimWhat exactly does that result support?

Bind evidence to the artifact or commit, relevant configuration, environment, inputs and time. A result for a different candidate or boundary does not prove this one.

04 / Test quality

Test-quality review

Optional reading checklist. Ticks are temporary local UI state, are not saved, and never change gate decisions.

Five check states

PASS
Observed evidence supports the named check for the named candidate and conditions.
FAIL
The check ran and its acceptance condition was not met.
BLOCKED
A dependency, permission, environment or other obstacle prevents the required check.
NOT_RUN
The check has not been executed.
NOT_APPLICABLE
A documented scope or design reason excludes the check. Missing infrastructure is not such a reason.
A passing suite supports only its observed checks and conditions. Inspect actual candidate-bound results; a queued job, green badge or agent summary alone is insufficient.

Record whether a check validates the candidate, tests a detector, or supplies historical context. In an isolated detector experiment, expected detection of a deliberate fault can PASS the detector check. Retain fault identity, detection and clean restoration/revalidation separately. Unexpected outcomes or failed restoration remain gaps; accidental failures cannot be relabelled afterward.

05 / Gate decisions

Gate decision rules

Establish scope, required coverage, applicability, evidence validity and dependencies. Include unresolved in-scope findings from every source. For obligations not covered by valid exceptions, apply this precedence:

  1. Any current required check/finding or required upstream gate is FAIL → gate FAIL.
  2. Otherwise, any required check or required upstream gate is BLOCKED → gate BLOCKED.
  3. Otherwise, NOT_RUN, missing/invalid evidence, unresolved applicability/coverage, an empty in-scope gate, or required upstream NOT_READY → gate NOT_READY.
  4. Otherwise, a valid accepted exception covers a gap or a required upstream gate is CONDITIONAL → gate CONDITIONAL.
  5. Otherwise, every obligation is covered, all applicable required checks/dependencies have valid PASS evidence, and no unresolved in-scope finding remains → gate PASS.

Exclude justified NOT_APPLICABLE checks. An in-scope gate with no applicable required checks is NOT_READY. A genuinely excluded phase is OUT_OF_SCOPE and contributes no assurance. G0–G2 can use observed document/review checks. Scope dependencies to the claim; release qualification requires applicable G0–G5 obligations. Required upstream conditions propagate until their gaps are resolved with evidence.

Accepted exceptions

Keep the underlying check state. An accepted exception needs all of the following:

  • A named, authorized decision maker and explicit approval evidence.
  • The affected requirement, risk, check, candidate/environment, allowed action and scope.
  • The underlying state and remaining uncertainty or consequence.
  • Compensating controls and evidence, or explicit authorized acceptance that none exists and why proceeding is acceptable.
  • An expiry or concrete revisit trigger and an accountable follow-up owner.

At the point of use, verify authority, expiry, candidate/environment, scope and current evidence that every condition is satisfied. An unsatisfied or expired exception cannot suppress the underlying gap. A plan for a compensating control does not prove the control works.

The agent cannot self-approve. Hard stops and claim-integrity requirements cannot be excepted by this skill. Scope, claim boundaries and authorization cannot be waived.

CONDITIONAL means permission to proceed within approved conditions. It never means “tests passed” or unconditional completion.

Permission to proceed

PASS or a valid CONDITIONAL permits dependent work only within the approved scope and authorization. FAIL, BLOCKED or NOT_READY holds dependent progression. Independent authorized work can continue.

A PASS gate does not authorize deployment, destructive changes, third-party communication or other actions outside the approved task. Confirm the applicable authorization before executing the action. A release can be qualified without being deployed, and authorized local work can be complete while optional deployment remains outside scope.

06 / Completion

Completion labels

Use these labels only when relevant gates and evidence support them within the authorized scope. An unqualified verification claim requires PASS for every supporting obligation. Passing subsets must be named as subsets; a lower label does not finish a larger assignment.

PROPOSED

Requirements, design or a test plan is written and reviewed to the stated extent. Implementation and executed product checks are not established.

IMPLEMENTED

Intended source changes are connected to the requested execution path within scope; actual checks and gaps are stated. Runtime correctness and task completion are not established.

LOCALLY_VERIFIED

Relevant checks passed in the named local environment and conditions.

INTEGRATION_VERIFIED

Named real component boundaries and effects were exercised with valid relevant G4 evidence. Untested boundaries remain unverified.

RELEASE_QUALIFIED

Applicable G0–G5 criteria have PASS evidence for the candidate and declared release scope. Deployment is not established.

DEPLOYED_OBSERVED

An authorized rollout occurred; identity and relevant outcomes were observed. Ongoing operation remains ongoing.

Audit/design completion requires the requested artifacts and their validation to be finished; identify product behavior that was not executed. Implementation completion requires all requested deliverables, integration, required validation, and relevant cleanup/handoff. A remaining failure, blocker, pending check, invalid evidence, or conditional gap prevents unqualified completion. Report “implementation finished; validation failed/blocked/pending” as applicable. G7 covers only a stated operational interval. For a CONDITIONAL gate, say conditionally approved to proceed, identify the exception and retain the strongest actually verified behavior claim. Do not use an unqualified RELEASE_QUALIFIED label. A factually observed deployment must retain any qualification condition.
